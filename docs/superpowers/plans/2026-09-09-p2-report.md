# #20-P2 报告：窄内核（两族 M=1 GEMV）落地

> G-P6 **双臂都已实测**（on **33.3** / off **32.3**，同一交付镜像、同一容器、同一 auto 时钟口径，
> 见"交付态"一节）。除 G-P6 落在 2026-09-10（主机两次掉电后续跑）外，其余六门的数字全部来自
> 2026-09-09 实测，证据文件在 `logs/p2/`，逐门执行记录在计划的各 Task Actual。

## 结论（先说答案）

1. **已进镜像**：`vllm-gfx906:latest`（`e806793fd238`）与 `:rebuilt`（`3db9747fd931`）两条构建路径都带
   P2，`.so` 由镜像自己从 `docker/patches/p2_w4a16_gemv.hip` 编出（源 md5 `af1535d6…`，与过门内核
   逐字节同源），全新容器 `gfx906-selfcheck` **23 ok / 0 FAIL**。默认开启，回退开关
   `VLLM_WNA16_P2_GEMV=0` 在交付镜像内实测生效（纯净容器 off 臂 `p2_gemv` launch **= 0**）。
2. **收益兑现的是 71–72% 的承诺**，且差额全在分母不在内核：引擎内 device 侧净收益
   **812–826 µs/step**，而计划承诺口径（1.3× 线）是 **1 148.7 µs**。P2 侧单次比承诺还快
   （实测 `p2_gemv` 54.3 + `p2_reduce` 5.1 = **59.4 µs**，G-P0 的 60.5/58.2），但**被换掉的
   incumbent 在引擎内只值 72.0 µs/调用**，而门用的是微基准分母 78.99/74.14 µs —— 权重长期
   驻留 L2 后分母变小，同一份内核能换回的时间就少了 22%。**这不是内核退化，是收益口径的
   分母与实测不同源**（[[gfx906-env-pitfalls]] 第 15 条的同一族）。
3. **数值上 P2 是"更干净的那条路"，而且是两个数量级**：真实权重/真实激活下 P2 对 fp64 零自由度
   参考 **RMS 0.0118–0.0331 ULP、MAX 1 ULP、重跑 8/8 逐位相等**；同操作数的现产线 ExLlama
   **RMS 29.7–94.1、MAX 6 592、自身重跑就有 71–74% 位置变动**（atomicAdd 顺序）。
   ⇒ 换内核同时买到确定性与精度，代价为零。
4. **语义零可见变化**：greedy 256 token **两臂逐位一致、0 处分歧**（引擎 A/B 与交付镜像各测一次，
   两次都是 256/256）；L3 的 margin 判据四条件全绿。
5. **本计划最大的缺陷不在内核而在分派位置**：G-P3 首跑 **FAIL**，`p2_gemv` launch 数 = 0、
   两臂逐位同速。根因是把 `M == 1` 写在 `apply_weights` 里 = 写在 dynamo 追踪区内，形状在
   trace 那一刻就被折叠、False 分支烤进编译产物。修复＝M 判断与 env 读取一起搬进 custom op 的
   **impl**（dynamo 不进 op 体），`apply_weights` 只留装载期常量 `self._p2_route`。这与 vLLM 自己
   的 M=1 skinny 分派同构，但**计划原文没写、评审也没抓到**，是实测抓出来的。
6. **G-P6 实测把"门高于可达上限"这条从预测变成了同机双臂 A/B**：交付态（auto 时钟、全新容器、
   开箱命令、同探针）**on 33.3 / off 32.3 tok/s** ⇒ **delta +1.0 tok/s（+3.1%）**；门 **≥33.4
   ⇒ 字面 FAIL 0.1**。三笔账要一起看：① 33.4 需要 924–1 020 µs 真实收益，而 G-P3 设备侧只有
   **812–826 µs** ⇒ 算术顶 **33.18–33.28**，**33.3 落在顶之上**；② serve 侧实测差值 =
   30.960 − 30.030 = **930 µs/step**，**比设备侧测到的还多 13%** ⇒ 换内核没有"设备侧赚、serve 侧
   亏"的隐藏折损；③ 兑现率 = 1.0 / 1.245（1.3× 承诺折算到本次 off 分母）= **80%**，与设备侧的
   71–72% 同一量级。⇒ 设备侧赚到的那份时间**全额转成了 serve 吞吐（无折损）**，不达标的原因是
   门定得比可达值高，不是实现不足。用户裁定**不放宽** ⇒ 这一条按字面 FAIL 入档；同时 off 臂 32.3
   与历史基线 32.4 差 0.1，说明"1425 钉频下 812–826 µs 平移到 auto 档"这条此前的假设在
   **基线复现**和 **A/B 差值**两处都对上了。

## 做了什么（范围与不做什么）

- 只换 **两族** M=1 decode：post-partition `(5120,8192)`（48 次/step）与 `(5120,7168)`（16 次/step），
  合计 64/256 次 WNA16 GEMV。M>1、其余三族、persistent kernel、FP8/attention **明确不在本计划**。
- 结构 = 生产 `.hip`（`p2_gemv` 主内核 + `p2_reduce` 归约，sk=10 单累加器）+ ctypes shim +
  `torch.ops.vllm.p2_gemv_or_fused` 运行期分派 + 装载期白名单 scratch。
- `.so` 缺失/符号缺失 ⇒ `_P2_OK=False` ⇒ **整条路径静默回退到现产线**，默认安全。

## 交付态（G-P6）

口径：交付镜像 `vllm-gfx906:latest`（`e806793fd238`）+ **全新容器** + **auto 时钟（已 unlock，
两卡都验过 `level=auto` 才开测）** + `gfx906-serve <MODEL_DIR>` 开箱命令，探针与
`p05_serve_probe.sh` 逐字同（REQ2_WARM = 64 token、temperature 0，32.4 那个基线就是从这一档读的）。

| 臂 | REQ2_WARM | DECODE256（3 次） | 说明 |
|---|---|---|---|
| **on（默认，无 env）** | **33.3** | 33.5 / 33.4 / 33.5 ⇒ mean **33.5** | 开箱即用态；`/proc/<serve>/environ` 里**没有** `VLLM_WNA16_P2_GEMV` ⇒ 走 impl 默认 1 |
| off（`-e VLLM_WNA16_P2_GEMV=0`） | **32.3** | 32.5 / 32.4 / 32.3 ⇒ mean **32.4** | 2026-09-10 08:20 主机恢复后由同一可重入脚本续跑取到（on 臂自动跳过）；`READY_AFTER=430s`、`torch.compile took 63.68 s`（复用同容器 AOT 缓存）、KV **64,322**（3.93×）、`wna16_exllama_lines=2` |
| 参照：P2 之前同一探针（另一 session） | 32.4 | 32.5 / 32.6 / 32.6 ⇒ mean 32.57 | 交付态旧基线；本次 off 臂 32.3 与它差 0.1 ⇒ 旧基线在**同一台机器上可复现** |

**门判定：REQ2_WARM 33.3 < 33.4 ⇒ 字面 FAIL，差 0.1。** 但同一句话必须连着说：
**33.3 落在算术顶 33.18–33.28 之上**（分母用历史 32.4：`32.4/(1−819/30860)=33.283`；分母用本次
同机 off 臂 32.3：`30.960−0.819=30.141 ms ⇒ 33.178`；819 = **G-P3 设备侧实测 812–826 µs/step 的
中点**，同一件事在 G-P5 纯净容器的 wall 口径是 789 µs = 32.765→31.976 ms）。
⇒ **不是"1.3× 承诺兑现了 100%"**（那笔账是 71–72%，见结论 2），而是**设备侧赚到的 812–826 µs
以 930 µs/step 的形式全额出现在 serve 上**（30.960−30.030）——**过不了的是门，不是代码**
（诚实账第 9 条由"预测"升格为"实测坐实"）。DECODE256 那一档 mean 33.5 ≥ 33.4，两档不一致本身也在
这张卡的抖动范围内（双稳机器态 ±0.7 µs/内核 ⇒ 每步 ±~20 µs ⇒ ±0.02 tok/s 量级，探针级差异读不出）。

**顺带把一条"假设"变成了"实测"**：遗留节里"1425 钉频下测的 812–826 µs 平移到 auto 档成立但未证"——
33.3 对 33.18–33.28 的吻合、加上 off 臂把 32.4 复现成 32.3，是它的两处直接验证（访存受限项不随
sclk 变）。

**双臂共用一份编译产物这个 A/B 前提，也被同一对臂的两个数字支持**：off 臂复用 on 臂留下的 AOT 缓存
⇒ 就绪时间 **690 s → 430 s**、`torch.compile` **387.51 s → 63.68 s**，而它的吞吐读数是 32.3 —— 与
当年**全新缓存**那次读到的 32.4 同值。⇒ 两臂之差来自运行期分派（env 在 op impl 里读），不是
"各臂自己编了一份产物"，G-P3 那条"env 读取必须躲开 dynamo 追踪区"的修复在这里第二次生效。

**双臂不对称之处只有一处，且方向不利于结论**：on 探针是在**冷卡**上跑的（05:03–05:05 采样
junction 43 °C、18/22 W 空闲），off 探针紧随 graph capture（08:23–08:25 junction 冲过
**106 °C**）之后、在 65–70 °C 的余温上开跑。也就是说**热态吃亏的是 off 臂**，而它给出的恰好是
较低的那个数 ⇒ 这处不对称只会让 +1.0 这个差值偏保守，不会把它做大。两臂的 REQ2_WARM 与三次
DECODE256 各自单调（on 33.3/33.5、off 32.3/32.4），没有交叉。

**掉电打断（不是本内核的问题，取证在案）**：Task 6 窗口内主机死两次。
① 04:31 首次启动在 torch.compile 期断电——`journalctl -b -1` 尾部无 shutdown 记录、
`user.journal corrupted or uncleanly shut down`、**所有**容器（含无关的开发容器）同一秒
`Exited (255)`、cache 只落 72 K（编译没跑完）。
② 05:12 第二次（off 臂启动后）再次失联。黑匣子（5 s sysfs 采样）在 ①→② 这段窗口取到
**junction 峰值 107 °C（阈值 temp2_crit=105 °C）、每卡 218 W（`power1_cap`=190 W 读数被越过）**，
与 [[gfx906-host-instability]] 的"双卡 init 期 THERMTRIP 概率性拉掉平台供电"完全同型；
on 臂本身 690 s 就绪、`torch.compile took 387.51 s`、KV 67 356 tokens、并发 4.11×，全程无异常。
⇒ 缓解已落进脚本：完成的臂跳过、容器复用（不再 `rm -f` 丢缓存）、失败原地重试，主机回来后
**同一条命令即可续跑**——08:20 的续跑一次成功（8.5 min 取到 off 臂），这条缓解措施已被验证。
③ **风险没有消失**：run 2 的黑匣子同样读到 **junction 106 °C（>crit 105）且每卡 265 W**（比 run 1
的 218 W 更高），只是这一次没触发断电。`power1_cap` 已经是 `power1_cap_max`=190 W ⇒ 宿主侧没有
"再压低一点"的旋钮可拧，交付态计时只能在冷卡窗口取。

## 执行期被证伪或改写的断言（诚实账）

写在这里是为了让"计划的门"不再被当成已验证事实：

1. **"漏 `mutates_args=[out]` ⇒ 输出恒零"** —— M3 变异实测**门仍全绿**，该后果在当前
   torch/vLLM 版本不复现。列全 `["part","out"]` 是 op 契约要求，不是门保护的不变量。
2. **"清 `VLLM_CACHE_ROOT` 能让 env 开关生效"** —— 指错了机制。真实原因是"dynamo 在追踪区内
   折叠了形状测试"，解药是把判断放进 op impl；缓存卫生保护的是"别复用别的模型/并行度的产物"。
3. **"L3 两臂的翻转位置集合必须相同"** —— 结构性不可能：on 臂的 drop 正是 P2 换 token 的结果。
   改判为比较交集 + 覆盖率 <90% 才 FAIL。
4. **"跨臂 prefill 对照应为 0 翻转"** —— 实测 4 处、worst 0.0469，全部来自**未改动路由**的
   atomicAdd 抖动（没换的比换了的翻得多）。它反过来成了 M₀_swap 的独立尺子。
5. **dispatch proof 的 `off==0`** —— 会 FAIL 掉健康臂：加载期预热不读该 env。判据改为**轮数**
   （off 1×64、on 3×64，族比恒 48:16）。
6. **"`_P2_HITS` 能当分派计数"** —— 修复前它在追踪区里，等于永远只记一次；现在它在 op impl 里
   才是真实计数，但仍不落盘 ⇒ 每步计数的权威证据是 **device trace**。
7. **1.3× 收益的算术**：本文前一版把 +1.25 说成"舍入边界差"，容器内重算 `32.4/(1−1148.7/30860)`
   = **33.6527 ⇒ +1.2527**，评审的 +1.25 才是对的。
8. **`.so` md5 当同源判据** —— hipcc 给每个 TU 打 `__hip_cuid_*` 并嵌入源路径，同源两份产物
   逐字节不同。判据 = **源 md5** + 滤 cuid 的 `strings` diff。
9. **G-P6 的门本身**（33.4 > 实测顶 33.18–33.28）—— 与评审当初抓"33.2 > 纯分派上限 33.16"
   同一类缺陷，只是这次是实测把分母压低造成的。off 臂到手后这笔账更硬：33.4 需要 924 µs（分母
   32.4）到 **1 020 µs**（分母 32.3），而设备侧只有 812–826。
10. **"探针文件存在 = 探针跑过"** —— Task 6 run 1 两头都错在自家工具上：
    ① `python3 - … | tee "$PROBE" <<'PY'` 里 heredoc 绑的是**流水线最后一段**（tee），于是
    `probe_on.txt` 收到的是一整份 python 源码、python 自己拿到 EOF，rc=120 却"有产物"；
    ② `cat f | ssh h 'cat > f2 && bash -n f2 && … &'` 中 `&` 把整条链后台化 ⇒ 后台任务 stdin
    被接去 /dev/null，远端文件写成 0 字节，而 **`bash -n` 对空文件是 PASS**。
    两处都按"门必须有牙齿"补上：探针落盘后 `grep -q "DECODE256 best=" || exit 1`，
    上传后比 md5 而不是比语法。
11. **"可重入"顺手摧毁了自己的证据** —— 续跑用**同名** `> p2_t6_serve.log` 重定向，把 run 1 那份
    driver 日志（含 on 臂 `READY_AFTER=690s`、`torch.compile took 387.51 s`）整份覆盖掉；臂级

## 遗留与风险

- **收益上限被分母锁死**：只要 incumbent 在引擎内继续"比微基准便宜"，P2 的可见收益就停在
  ~0.8 ms/step。想把 1 148.7 µs 真兑现，得去动**被替换项的定价**（L2 驻留）而不是 P2 本身。
- **7168 一族字面未达 1.3×**（1.274×），靠累计口径放行；只上 8192 一族的话收益是 +0.959 tok/s。
- **`p2_reduce` 用 `part` 的固定地址**：scratch 只在白名单层分配（约 2 层/卡），不是全局；
  但 `splitk` 与 `part` 行数由同一个 `_P2_SPLITK` 决定，改这一个常量即同时改分配与传参。
- **双稳机器态**：同一段代码两次跑差 ±0.7 µs（G-P1），任何 <1 µs 的单次差异在这两张卡上
  不构成结论。
- **交付时钟平移已从假设变成实测**（G-P6 双臂）：1425 MHz 钉频下 812–826 µs/step 的收益，在
  auto 时钟的 serve 上以 930 µs/step 兑现，且 off 臂把历史 32.4 基线复现成 32.3 ⇒ 平移成立。
  残留的不确定性只有一条：两臂的热态不严格相同（on 冷卡 43 °C / off 余温 65–70 °C），方向上
  让 delta 偏保守。
- 未 commit、未 `docker commit` 开发容器：交付只走两路径配方。
