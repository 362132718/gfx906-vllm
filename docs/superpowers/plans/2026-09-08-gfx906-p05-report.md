# #20-P0.5 报告：M=1 稠密 fp16 GEMM → skinny `LLGemm1_kernel`

## 结论（先说答案）

**decode step 53.66 ms → 33.01 ms，18.6 → 30.3 tok/s（+62.6%），256/256 贪心 token 逐字一致，已进交付镜像。**

上面是 1425/1000 MHz 钉频 + 离线 harness 的保守口径。**交付态（sclk auto，走 `gfx906-serve`）实测
32.4 tok/s**，与 P0.5 之前同一探针的 22.0 tok/s 直接可比 ⇒ **+47%**；冷启动 710 s / warm 420 s
均未劣化。详见「交付态复测」。

做法不是写内核，是**换调度**：gfx906 上 vLLM 的稠密 M=1 GEMM 全部落在 Tensile 的
串行 K 循环里（`in_proj_ba` 48×318 µs + `lm_head` 6 982 µs = 22.2 ms/step = 41.4%）。
ROCm 后端本来就有为 `n==1` 写的 skinny 内核，且已经用 `PYTORCH_ROCM_ARCH=gfx906` 编进了
`_rocm_C` 并实测可跑 —— 只是 vLLM 的 `use_skinny` 分支被 `_ON_GFX9` 挡在门外（见下）。
一条 10 行的门谓词就把这 22.2 ms 变成了 1.71 ms。

同一张卡的账（锁 1425/1000 MHz）：`lm_head` 每步读 1.271 GB 权重，1 468 µs ⇒ **865.9 GB/s
= 实测 `BW_eff`(931) 的 93.0%**。这一项已经没有肉可割；剩下的整块头寸是 W4A16 GEMV 的
**19 867 µs/step 对 6 788 µs 地板**，即 #20。

## 改动（全部改动 = 一处谓词）

`vllm/model_executor/layers/utils.py`，在 `rocm_unquantized_gemm_impl` 里、上游 `use_skinny`
块之后新增（权威副本 `docker/patches/layers_utils.py`，md5 `55379cbd…`，基线 `43a4addb…`）：

```python
use_gfx906_gemv = (
    envs.VLLM_ROCM_USE_SKINNY_GEMM
    and on_gfx906()
    and x.dtype in [torch.float16, torch.bfloat16]
    and bias is None
    and n == 1
    and m % 4 == 0
    and k % 8 == 0
    and k <= 8192
    and skinny_operands_compatible
)
if use_gfx906_gemv:
    x_view = x.reshape(-1, x.size(-1)).contiguous()
    out = ops.LLMM1(weight, x_view, 4)
    return out.reshape(*x.shape[:-1], weight.shape[0])
```

**为什么不直接把 `on_gfx906()` 加进 `_ON_GFX9`（两点，都是实测）**：

1. 上游那条 `use_skinny` 里 `wvSplitK` 排在 LLMM1 **前面**（`if m > 8 and 0 < n <= 5`），
   加宽 arch 谓词会让 gfx906 走进一条从未在这张卡上验证过的 Split-K 路径，且 `n` 范围不对
   （我们要 `n==1`、`m` 是输出维）。
2. `ops.LLMM1` **不校验 stride**：给它转置视图会静默返回垃圾（实测 rel = 1.357，不抛异常）。
   所以 `weight.is_contiguous()` 是必需的护栏，而不是风格问题。

`_ON_GFX9` 有意排除 gfx906 ⇒ 项目里凡是"ROCm 有快路径但没生效"的判断，先看这类 arch 谓词，
不要怀疑内核没编进来。

## 已知偏差（读数时请带上）

1. **锁频 1425/1000 MHz，交付态是 1700/auto** ⇒ 本文所有 ms 绝对值偏慢（保守），比例关系不受影响；
   本文的钉频读数不做事后换算，交付态实测见下一节「交付态复测」。
2. `ab_on` 的 `EXPECTED_MS=33.1` 是**我注入的门限值**，不是引擎产出；它只用于让脚本自己判红绿。
3. lm_head 数值门是 **8192/248320 行等距抽样**（全量 fp64 要 127 GB）；margin 统计是抽样下界。
4. bf16 放开依据是 Task 1 裸测（bf16 rel 3.8e-3 < 5e-3 但**接近门**，且 Tensile 在 bf16 下慢
   24× 更多）⇒ 若将来遇到 bf16 直发的模型，数值门要重跑。
5. 收益完全依赖 `n==1 && m%4==0 && k<=8192`。本模型恰好两个形状都命中；`k>8192` 或带 bias 的
   M=1 GEMM 仍在 Tensile 上（谓词故意不接管）。

### 回滚点归档（#18 的第一份实测，最终轮）

**为什么今天有三个 image ID**：`QUICKSTART.md` 是随镜像分发的（`COPY entrypoint/`），所以每改一次这份
文档就要走一遍 B→A ⇒ `1e18c8ea6b8b`（P0.5 门轮）→ `6ec669c822e8`（换实测基线数字那轮）→
**`b5931bb5c742`（最终，含 §1 磁盘需求与 §8 tok/s 修订）**。三者只差这一个文本文件，Path B 产物
相应为 `0d2dc5a67297`。**权威归档 = `vllm-gfx906-b5931bb5c742.tar.gz`**，前两份留着无害
（磁盘 305 GB 空闲），但它提醒一件事：**改镜像内文档不是免费的，攒够一批再走一轮。**

`/home/x/image-export/vllm-gfx906-b5931bb5c742.tar.gz` = **21,948,506,214 B（20.44 GiB）**，
sha256 随文件落盘。

| 量 | 实测 |
|---|---|
| `docker save` 原始流 | **22,070,416,384 B** |
| 归档（`save \| pigz -p 6`） | 21,948,506,214 B ⇒ **省 0.6%，1.01×**，耗时 261 s |
| 归档自包含性 | tar 共 **32 个成员，成员字节和 22,070,390,489 = 原始流的 100.0%**；三个 ~7.3 GB 的 blob 占全文 **99.6%** |
| 完整回读 | `pigz -dc \| tar -tvf -` 全量走完 **21 s**（顺带校验 gzip 流未损坏） |
| `docker load` 往返 | `Loaded image: vllm-gfx906:latest` + `LOADBACK_ID_MATCH` |
| 全程 | `NO_REBOOT_DURING_RUN` |

**为什么压不动（已查证，不是猜测）**：宿主 docker 用的是 **containerd 镜像存储**（`Storage Driver:
overlayfs` + `driver-type: io.containerd.snapshotter.v1`，media type `oci.image.index.v1+json`），
`docker save` 导出的是 `blobs/sha256/<digest>` 形式的**已压缩层 blob**（所以 tar 里根本没有
`layer.tar` 这个名字）。这同时解释了两件一直对不上数的事：`inspect .Size` 是 22.07 GB（压缩态之和）
而 `docker images` 是 69.8 GB（解包态）。

**给 #18 的结论**：网络上只需要过 **~22 GB**，但**对方磁盘要准备 ~70 GB 解包空间** —— 这两件事在
containerd 存储下不是一回事，别按 69.8 GB 去估算带宽，也别按 22 GB 去估算对端磁盘。任何"再压一遍"
的优化都是白工（0.6%）。

**订正一处方法论错误**：第一轮我也报过"只省 0.5%"，数字恰好没错，但分母拿的是 `inspect .Size`
而不是实测的 save 流字节数，而且当时 `docker images` 明晃晃写着 69.8 GB 我却没有调和这个矛盾。
这一轮把分母、成员求和、存储驱动三样都量了才敢下结论。凡是"体积/比率"类结论，先量分子分母再说话。

### 本轮抓到的自身缺陷（都是探针/工具的，不是被测系统的）

1. `docker exec` 少了 `-i` ⇒ heredoc 的容器内脚本**根本没进去**，`serve_once` 瞬间返回 0，Phase 1
   静默空跑（日志表现为两个时间戳相同）。凡是往容器里喂脚本，一律 `docker exec -i`。
2. 探针硬编码 `model=qwen38` ⇒ 全部 **HTTP 404**。`serve.sh:62` 是
   `--served-model-name "${SERVED_NAME:-$(basename "$MODEL")}"`，不导出 `SERVED_NAME` 时模型名就是
   目录名。改成从 `/v1/models` 解析真实 id（QUICKSTART §4 其实早就写了这一句，是探针没照做）。
3. 附带：teardown 后 `pgrep -cf` 报"6 个残留"实为 `<defunct>` 僵尸（容器 PID 1 是 `sleep infinity`，
   不 reap），util 0% / 双卡 17.1 GB 空闲 ⇒ 计数不等于占用。
